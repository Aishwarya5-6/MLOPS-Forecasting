## Question

In automated champion/challenger promotion, how do the **promotion rule** and the **validation-window length** affect harmful model swaps and the accuracy of the model actually deployed?

## What was run

| Item | Value |
| --- | --- |
| Datasets | Hyderabad CAMS (2025-11 → 2026-11), CPCB Hyderabad / Delhi / Bengaluru / Chennai (2019-07 → 2020-06). Kolkata and Mumbai were excluded by the eligibility rule (~410 days of history, 730 required) |
| Candidates | seasonal naive, SARIMA, XGBoost, tuned XGBoost, LSTM, ensemble. The extra cities have no LSTM |
| Replay | 52 weekly decisions; refit every 30 days; each swap judged on the following unseen week |
| Policies | τ ∈ {0, 1, 2, 5, 10}%, DM test (p < 0.05), never switch, oracle (hindsight bound) |
| Windows | V ∈ {7, 14, 30} days |
| Compute | about 1.5 h in total on an M4 MacBook Air, almost all of it LSTM refits |

## Results

Hypotheses are scored mechanically over 5 datasets × 3 windows = 15 cells ([reports/study/hypotheses.json](../reports/study/hypotheses.json)):

| Hypothesis | Holds | Verdict |
| --- | --- | --- |
| H1: τ=0 makes more harmful swaps than τ=2% and τ=5%, without being more accurate | 13 / 15 | **Supported** |
| H2: a DM test beats τ=2% | 5 / 15 | **Not supported** |
| H3: longer windows reduce harmful swaps | 12 / 15 | **Mostly supported** |

Key numbers, all generated in [paper/numbers.tex](../paper/numbers.tex):
- **τ=0 with V=7:** 30–44 swaps a year, of which 36–55% were harmful.
- **τ=5% with V=30:** 2–6 swaps a year. Deployed RMSE −1.9% to +1.0% versus τ=0.
- **DM rule:** 4–10 swaps a year with V=7 and 2–5 with V=30. Too cautious, and not more reliable.
- **Never switching** depends on the starting model: best in Bengaluru (−1.7%), worst in Chennai (+7.1%).
- **Exploratory:** the best single model, kept all year, beat every policy in 3 of 5 datasets.

**Practical takeaway:** promote only on a 2–5% improvement measured on about 30 days of recent forecasts.

## Problems hit

1. **Laptop heat:** the LSTM refits slowed from about 87 s to about 150 s per refit (thermal throttling). The fix was to queue jobs one after another instead of in parallel, and to run the station LSTM on 4 threads (protocol D1).
2. **Kolkata and Mumbai excluded:** both failed the 2-year-history rule. No substitute cities were added.
3. **A hand-typed number was wrong:** the draft said "3–12%" for the oracle gap; the data says 2.6–10.0%. All cross-dataset ranges are now macros, and a script checks that every `\R{}` key exists.
4. **H2 interval missing on the first run:** added and recorded as D2.1.
